z/TPF programming conventions The z/TPF system has established certain programming conventions to achieve high performance and ease program maintenance. It is important that the application conform to these conventions. The z/TPF system enforces some of the conventions; only good programming discipline can maintain others. Some of these conventions have been mentioned already and some will be discussed, in detail, in later sections. Common programming conventions The following conventions apply to z/TPF applications programming in general. All application programs must be reentrant. They must not contain any internal switches, indicators, or counters. Do not modify the fields in the ECB that the z/TPF system maintains. These fields include, but are not limited to, core block reference words, the z/TPF register save area, and other control information. Refer to these fields as necessary. Remember that the z/TPF system does not necessarily clear or initialize any working storage blocks before assigning them to the application program. All working storage blocks begin on a doubleword boundary. Symbolic references must be maintained in all areas. This will enable programming to be configuration independent and system parameters to be changed without extensive programming effort. In assembler language no absolute address constants can be used; the technique of subtracting one label from another in order to obtain an actual byte count of the distance between the two locations can be used, provided the two labels are defined within the same program segment or data record. Also in assembler language the names for all storage locations, registers, and I/O devices should be symbolic. Use of absolute values of all types should be minimized. In C/C++ language only put absolute values in headers and associate symbolic names with these values. Use the TPF_regs structure in C/C++ language for passing data in registers to programs where registers must be specified. When your application programs will operate on any I-stream of a multi-engined central processor complex (CPC) , follow the rules of multiprogramming and multiprocessing as described in the z/Architecture Principles of Operation . In general, the z/TPF system will handle the serial access to data records via the normal system services (for example, getcc , relcc , find_record or FINDC, file_record or FILEC, fiwhc , filuc ). However, when your application interacts with a shared resource, such as a common global, use appropriate multiprocessing techniques to access and update these areas. Ensure that your application programs return control to the z/TPF system within 500 milliseconds of activation. Control might be returned in several ways; for example: Call the waitc function while waiting for I/O activity to complete. This is required for any find request. A program might call the waitc function explicitly, or may call another function (for example, a fiwhc function) that, in turn, performs a wait. Note that waitc returns control to the application program, and resets the 500-millisecond timer, only after all I/O activity for the ECB actually has completed. Call the dlayc or defrc function partway through the program logic to place the entry of the program at a lower priority than other work. You might use this method if the program does little I/O activity, but might run slowly enough to risk breaking the 500-millisecond limit. Call the exit function to end processing of the program. Most application programs are transaction- and I/O-oriented, so they return control to the z/TPF system frequently with each waitc . The timing constraint usually only becomes a concern if the programs will be retrieving much of their data from the virtual file access area. Such retrieval does not reset the 500-millisecond timeout counter. For more information, see Virtual file access facility . Ensure that all application programs call a waitc function, either explicitly or implicitly, after a read or write request to ensure that the I/O is complete before trying to use the requested resource, for example, the file record to be read with a Find function. For more information, see Summary of file reference functions and macros . Ensure that application programs return any system resources not in use or imminently planned for use. This is an important discipline. All system resources (such as main storage blocks and file pool addresses) should be returned promptly. Because many ECBs operate concurrently, failure to do this could be a significant drain on system performance and require excessive resource allocation. During execution of a z/TPF API function, a variety of exceptional conditions may be detected. Application programs regain control only on I/O hardware errors or I/O-associated unusual conditions related to a unique entry. A function parameter error results in a forced exit and a dump. The z/TPF system takes a dump and sends an operator message only on I/O hardware errors. These conditions are recorded in the ECB on return to the application program from the z/TPF API function. Use the find-and-hold functions to hold all file storage records before you update them, to ensure the proper sequence of update. For more details, see Record hold facility . Ensure that your program holds only one record at any given time, to prevent a lockout condition from occurring. Assembler language programming conventions The following list summarizes the assembler language programming conventions: Do not issue privileged instructions in application programs; also, do not explicitly issue the supervisor call (SVC) instruction. Do not use the restricted-use control program macros described in System programming services in application programs. Only the general use control program macros and the general purpose application macros are appropriate for application programs, because only these macros are guaranteed to be compatible with later z/TPF releases. The general registers 0 through 7 are reserved for use by application programs. Their contents are saved across all control program macros. Registers 14 and 15 may also be used by application programs, but are often used by the control program to pass information between programs. The contents are not guaranteed across macro calls unless otherwise indicated. General register 8 always contains the base address of the active application program. It must not be altered by application programs. General register 9 always contains the address of the current active entry control block. It must not be altered by application programs. General register 10 can be used as a scratch register (the contents are not guaranteed across macro calls). General registers 11 and 12 are reserved for control program use. Their contents must not be modified by an application program. Register R11 contains a value of X'1000' and register R12 contains a value of X'2000'. General register 13 can be used as a scratch register (the contents are not guaranteed across macro calls). General registers 10 to 13 can be used by application programs that use the extended register save function either by coding the EREGSAVE parameter on the BEGIN macro or by using the DEFBC macro. By using the extended register save function, the contents of R10–R13 are saved across all general macro calls. All storage is assigned by the control program. You do not, in general, code define storage (DS) commands in your own application program to describe storage block formats. Instead, your program requests storage blocks from the control program and uses the z/TPF system or user data macros to describe the formats. An application macro might generate inline code or an SVC through the use of a control program macro. The SVC machine instruction is never directly used by an application. In the z/TPF system , if macro expansion code that includes branch relative instructions is processed outside of the core resident program area (CRPA), unpredictable results can occur. If you need to move generated code, code the DEFBC macro with RELATIVE=NO specified around the macro call that uses branch relative instructions. You can use branch relative target check mode to identify programs that use branch relative instructions for branch targets outside of a program. For more information, see Branch relative target check mode (APAR PJ31568) . C language programming conventions The following list summarizes high level language conventions: Programs that run on a z/TPF system can access ECB heap in 31-bit or 64-bit addressing mode. C shared object (CSO) types include: Single entry point with a maximum of one main function. Single entry point without a main function, which can include program libraries, or nonprogram libraries, or a combination of both. Nonprogram libraries. For more information about CSOs, see Create a C shared object . Use the system function to activate a high level language program that contains a main function. Follow the register conventions established in the z/TPF Program Development Support Reference when coding programs that interact between assembler and C language support.

REXX APIs The REXX APIs are used for connectivity to the TPF Operations Server for automation programs written in the REXX programming language. Open Object Rexx provides the interpreter for REXX programs. Use the REXX APIs to attach a RAVEN variation to a TPF Operations Server . Other REXX programs can make use of the API as well through the following REXX system calls: call RxFuncAdd ApiLoadFuncs, TOSREXX, ApiLoadFuncs call ApiLoadFuncs For more information about RAVEN, see REXX Automation Variation Environment (RAVEN) . For more information about how to set up a REXX system call, see the Open Object Rexx website. To reduce the number of parameters needed by the REXX API functions, the REXX APIs use stem variables to describe message lines and commands. For example, a stem variable can contain information about the attributes assigned to a message line or command. This feature can help to simplify your program and improve performance. The REXX API stem variables are created when your program initializes the API by calling ETOSR_Open . Stem variables are similar to structures and records used in other high-level languages. Just as structures contain members, stem variables contain compound variables. These compound variables can be accessed by specifying the name of the stem variable, followed by a period (.), followed by the name of the compound variable. For example, to access the compound variable named szImageName in the stem variable named ETOSR_Rcv, you must specify ETOSR_Rcv.szImageName. Whenever your program receives a message line or command from the input queue, the REXX API places additional information about the message line or command in the appropriate stem variable. For example, the REXX API can place information about the console session that is used to route the message line or command to your program in one stem variable and place information about the attributes that are assigned to the message line or command in another stem variable. The REXX APIs use the following stem variables and global variables to communicate with your program: ETOSR_Ctl: When your program receives a message line or command from the input queue, this stem variable receives information about the console session that is used to route the message line or command to your program. For example, this stem variable receives the name of the TPF host system for which the console session was started. For more information about the ETOSR_Ctl stem variable, see ETOSR_Receive – Receive messages . ETOSR_Rcv: When your program receives a message line or command from the input queue, this stem variable receives information about the message line or command that was routed to your program. For example, this stem variable receives information about the attributes that are assigned to the message line or command. For more information about the ETOSR_Rcv stem variable, see ETOSR_Receive – Receive messages . ETOSR_hConsole: This global variable is set when the ETOSR_Open function is called. This is the session handle used with other REXX API calls. See Programming considerations for more information about the ETOSR_hConsole global variable. REXX APIs consist of the function calls that follow and are available in C header file ETOSR.H . For migration purposes, the enginename tag was previously called classname . However, the REXX APIs will continue to support filter.F x .classname in the session configuration file. Additionally, coding the enginename tag or the classname tag as com.ibm.tpf.etos.TPFilter.Filterengine will refer to the TPF Operations Server default console filter engine DLL (TOSFilterEngine.DLL).

TPF Operations Server product overview The TPF Operations Server product is a console automation and enhancement application for the TPF system . This PC-based application provides a tool for the administration and maintenance of your TPF system through TPF operations consoles. The TPF Operations Server runs outside the TPF system complex and provides support for you to monitor multiple TPF systems from a single workstation, automate operational tasks, and diagnose problems quickly and accurately. By using the TPF Operations Server product in your enterprise, you can improve TPF system availability by decreasing the likelihood of operator error and reduce the number of unplanned outages, provide hardware and software redundancy to improve operational console availability, and automate operational processes that include those for starting and stopping a TPF system .

REXX Automation Variation Environment (RAVEN) RAVEN is an automation package that simplifies the writing and operation of automation for the TPF Operations Server platform. Automation can be written with the RAVEN package by using scripting languages or written in REXX subroutines. RAVEN automation is made up of variations for automation purposes. The term variation is similar to a task. RAVEN variations can be short-running or long-running automation tasks. An example of long-running automation task is a variation monitoring the usage of tapes on an active TPF system . An example of a short-running automation task is a variation to cycle a TPF system to norm state. Once the TPF system reaches NORM state, the variation exits. RAVEN allows you to consolidate these different automation tasks to simplify control and monitoring. There are many sample variations supplied in the RAVEN variation directory (\RAVEN\VAR) that you can use as a guide while writing your own variations. In particular, look at the TESTnnn variations. These perform very simple functions but exercise many of the supplied routines. The automation is based on a variation structure, each variation having its own file coded in REXX. For example, the variation for IPLing the TPF system might have a file name of IPLB001.VAR. Each variation file (*.VAR file) is processed as several subroutines of a mainline routine. The mainline routine is located in the INCLUDE.VAR file. When a variation is activated through AUTO ACT, the automation creates a REXX command file (*.REX) by combining the INCLUDE.VAR and < variation >.VAR files into the < variation >.REX file. For example, if the IPLB001 variation is activated through AUTO ACT IPLB001, the automation program will create the IPLB001.REX REXX command file by combining two or three files: INCLUDE.VAR *.SUB (optional) IPLB001.VAR. The INCLUDE.VAR file handles all the queuing between the RAVEN mainline program (AUTO.REX) and the variation program. Several subroutines are contained in each variation file (*.VAR): VARIATION_DESCRIPTION. See Routine: VARIATION_DESCRIPTION for more information. START_UP_TASKS. RAVEN and other automation techniques You can write separate automation programs for each different automation goal. The advantages of RAVEN over multiple automation programs are: As you will see after reading the RAVEN Programmer's Guide , variations are very simple to write and maintain compared to multiple automation programs. RAVEN has one simple operator command that can be used to activate, monitor, and deactivate the variations. If you were to write 30 different automation programs, you would have to create 30 different commands to activate, monitor, and deactivate your automation programs. Because RAVEN contains all the routines needed to communicate with the operator or host, and supplies these routines to the variations in simplified form, the variations themselves are very simple to write and maintain. If you were to write 30 different automation programs, each program would have to contain its own host and operator communication routines. This raises again the maintenance issue. RAVEN variations can communicate with each other by passing data to the mainline program which then sends the changed data to all variations. If you were to write 30 different automation programs, you would have to write your own inter-variation communication routines. The RAVEN mainline program monitors the host state. The variations are kept apprised of changes in the host state via global variables. If you were to write 30 different automation programs, you would have to monitor and maintain your own host state variables. Since the RAVEN design is based on a mainline program and dependent variation subroutines, all the variations can be paused simultaneously if problems occur. The variations can then be unpaused using one command. If you were to write 30 different automation programs, you would have to develop some mechanism to pause and unpause all the programs. RAVEN has a special variation called MULT whose sole purpose is to activate and monitor other variations. This facility would be difficult to write (and maintain) for many different variations. RAVEN has a special variation called TDRV that is driven by file input. It can be used to validate host responses to input messages for TPF base code and TPF application code. This facility would require its own program. RAVEN has a special variation called MTRP that is driven by file input. It can be used to monitor host output messages for indefinite periods of time. This facility would require its own program. RAVEN has a message trap function that can activate variations or commands when specific host output messages are found. This facility would be very difficult to write (and coordinate) over different variations. RAVEN allows variations processing on one workstation to communicate with variations executing on another workstation. This facility would be very difficult to write (and coordinate). RAVEN is also a good tool to consolidate several existing REXX automation programs by converting them to RAVEN variations.

Built-in functions REXX provides a rich set of built-in functions, including character manipulation, conversion, and information functions. There are six other built-in functions that TSO/E provides: EXTERNALS, FIND, INDEX, JUSTIFY, LINESIZE, and USERID. If you plan to write REXX programs that run on other SAA environments, note that these functions are not available to all the environments. In this section, these six built-in functions are identified as non-SAA functions. In addition to the built-in functions, TSO/E also provides TSO/E external functions that you can use to perform different tasks. These functions are described in TSO/E external functions . The following are general notes on the built-in functions: The parentheses in a function are always needed, even if no arguments are required. The first parenthesis must follow the name of the function with no space in between. The built-in functions work internally with NUMERIC DIGITS 9 and NUMERIC FUZZ 0 and are unaffected by changes to the NUMERIC settings, except where stated. This is not true for RANDOM. Any argument named as a string may be a null string. If an argument specifies a length , it must be a positive whole number or zero. If it specifies a start character or word in a string, it must be a positive whole number, unless otherwise stated. Where the last argument is optional, you can always include a comma to indicate you have omitted it; for example, DATATYPE(1,) , like DATATYPE(1) , would return NUM . If you specify a pad character, it must be exactly one character long. (A pad character extends a string, usually on the right. For an example, see the LEFT built-in function on page LEFT .) If a function has an option you can select by specifying the first character of a string, that character can be in upper- or lowercase. A number of the functions described in this chapter support DBCS. A complete list and descriptions of these functions are in Double-byte character set (DBCS) support . Restriction: LISTDSI does not support files in the UNIX file system. It is a TSO/E external function and can be used only in REXX execs that run in the TSO/E address space.
